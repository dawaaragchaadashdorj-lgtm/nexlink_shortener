# Render deployment (free, Postgres-backed)

Links are stored in an external Postgres database, so the service needs no
persistent disk and can run on Render's free web-service plan.

## 1. Create a free Postgres database

Use any free managed provider (Neon, Supabase, Railway, Aiven, etc.) and copy
its connection string. Prefer a **pooled** connection string if the provider
offers one. Keep it secret; it grants full access to your links.

## 2. Prepare the repository

The repository root is the folder containing `package.json` and `render.yaml`.
Do not set `rootDir: nexlink-shortener`.

`render.yaml` defines one free Node web service in Singapore. `DATABASE_URL`
uses `sync: false`, so it is **not** stored in Git — you enter the real value in
the Render dashboard.

## 3. Deploy

1. Connect the GitHub repository to Render.
2. Create a Blueprint using the `codex/render-deployment` branch and `render.yaml`.
3. Approve creation (free plan; no disk).
4. In the service **Environment**, set `DATABASE_URL` to your connection string.
5. Retrieve `CREATE_ACCESS_TOKEN` privately (Render generated it). This is the
   owner key required to create links in production.
6. Trigger a manual deploy (auto-deploy is off) and wait until healthy. Render
   assigns an HTTPS `onrender.com` URL.
7. Open the site, create a link, and enter the owner key when prompted. Do not
   share the owner key with link recipients.

Only the owner can create links in production. Anyone with a short link can open
it, subject to that link's password and schedule. The owner key stays in memory
in the current browser tab; it is not saved to local storage or embedded in the
bundle.

## Custom domain (optional)

Buying a domain is not required — the `onrender.com` URL works as-is. To use your
own domain later:

1. In `render.yaml` add `domains: [your-domain.com]` and an `APP_ORIGIN` env var
   set to `https://your-domain.com` (matching exactly, no trailing slash), or add
   both through the Render dashboard.
2. Add the DNS records Render shows at your registrar. SSL is issued automatically.

`APP_ORIGIN` matters: `lib/request-security.ts` derives the public origin from
`APP_ORIGIN || RENDER_EXTERNAL_URL || request.url`. Without it, requests arriving
on a custom domain look cross-origin and link creation returns `403`.

## Environment

| Name | Value / purpose |
| --- | --- |
| `DATABASE_URL` | Postgres connection string; required in production |
| `CREATE_ACCESS_TOKEN` | Generated by Render; required for production creation |
| `NODE_ENV` | `production` |
| `RENDER_EXTERNAL_URL` | Provided by Render; used for origin validation |
| `APP_ORIGIN` | Optional; set to `https://your-domain.com` for a custom domain |
| `DATABASE_SSL_REJECT_UNAUTHORIZED` | Optional; `false` disables cert verification if a provider requires it |
| `DATABASE_POOL_MAX` | Optional; Postgres pool size (default 5) |

Do not put secret values in `NEXT_PUBLIC_*` variables, Git, chat messages, or
screenshots.

## Verification after deployment

- `GET /api/health` returns `200` with `{"status":"ok"}` (confirms DB connectivity
  and schema).
- Unauthenticated `POST /api/links` returns `401`.
- Create a link in the UI with the owner key and open it from another device.
- Check a password-protected link with both wrong and correct passwords.
- Redeploy or restart the service and confirm a previously created link still
  redirects (proves data lives in Postgres, not the instance).
- Generate a QR code on the deployed site and scan it with a phone.

Optionally run the Postgres integration test locally against a throwaway DB:

```sh
TEST_DATABASE_URL="postgres://..." npm test
```

## Operations

- Keep one service instance for predictable in-memory rate limits. Creation is
  capped at 60 authorized requests/minute; password checks at 10/minute per link
  and 120/minute overall. Limits reset on restart.
- The free plan sleeps after inactivity; the first request may take ~50s to wake
  the instance. Data is unaffected because it lives in Postgres.
- Back up the Postgres database through your provider. Links are durable across
  redeploys; do not delete the database.
- Localhost links (file storage) do not migrate automatically; create new ones on
  the deployed URL.
- Roll back a failed release through Render's deploy history.
